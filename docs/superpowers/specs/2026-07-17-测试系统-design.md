## 1. 背景与使命

### 1.1 现状

CDFEG 系统分三层：核心库 `CDFEG`（C++14 DLL）→ 7 个 `sample` 示例（可执行程序）→ `pyTool` 代码生成器（Python）。现有"测试"零散不成体系：

- `pyTool/test/*.py` 多为无断言的生成器驱动脚本（仅 `test_preParser.py` 有断言）；
- `FEMproject/test/el2dData/` 是手工回归对比的工作目录；
- 新增未跟踪的 `test/models/{del2d1,hel2d1}.gid/`（含 `.dat` 输入 + `.post.res` 黄金基准）——端到端回归的雏形；
- 无任何 C++ 单元测试框架，无自动化回归，无 CI。

项目自有的验证哲学（见 rules）：以旧 C 基准 `mfel/macs` 的 `.post.res` 为黄金解，逐节点逐分量对比，要求 `max|Δ| ~ 1e-10`（机器精度），目前全靠手工 `awk+sort+paste`。

### 1.2 核心使命（用户明确）

> **测试系统的首要使命是回归测试**：用户会持续修改基础库代码，需要冻结"当前被信任的正确输出"，改库后自动跑全部示例并量化漂移，**守住计算结果的稳定性**。

次要使命：核心库单元级快速反馈；pyTool 解析正确性；解析解物理校验（留接口）。

### 1.3 重要边界（用户明确）

- **pyTool 只生成框架，`FEMproject/sample` 是完整手写代码，不全由 pyTool 生成** → 不必测试"生成代码与现有代码相同"。生成器测试降为可选独立项，不进主回归流程。
- 测试系统仅通过构建产物与配置驱动 CDFEG，**不侵入核心库源码**（唯一改动：根 CMakeLists 加一个默认 OFF 的 option）。

| 维度 | 决策 |
|---|---|
| 覆盖层次 | e2e 回归（核心）+ 核心库 C++ 单测 + 解析解（留接口）+ pyTool 生成器（可选独立） |

## 3. 整体架构与目录布局

测试系统是独立 Python 包（`test/`），通过 subprocess 编排全链路。**不侵入核心库源码**（仅根 CMakeLists 加 option）。

```
test/
├─ run_tests.py            # 唯一入口：python run_tests.py --suite all
├─ config.toml             # 工具链/路径/容差/用例注册（集中配置）
├─ framework/              # 编排框架（薄层，职责单一）
│   ├─ builder.py          #   cmake+make：构建 sample 与 unit_test
│   ├─ runner.py           #   跑 .exe，收集 stdout/退出码/.res
│   ├─ comparator.py       #   解析 .post.res，逐项数值对比 max|Δ|
│   ├─ parser.py           #   .post.res 解析（GiD 格式）
│   └─ report.py           #   汇总 PASS/FAIL，分级报告，退出码
├─ suites/
│   ├─ e2e/                #   端到端用例定义（指向 models/ 基准）
│   ├─ unit/               #   C++ Catch2 单测源码 + CMakeLists
│   │   └─ third/catch.hpp
│   ├─ generator/          #   pyTool 解析正确性测试（pytest，可选）
│   └─ analytical/         #   解析解算例（首批空，留接口）
├─ models/                 #   黄金基准 .dat/.post.res（git 跟踪）
│   ├─ del2d1.gid/         #   DEl2D：del2d.dat / del2d.post.res (+.accuracy)
│   └─ hel2d1.gid/         #   Hel2D：hel.dat / hel.post.res
├─ build/                  #   测试专用构建目录（gitignore，隔离）
└─ reports/                #   最近运行报告 + update_log.txt（gitignore）
```

**数据流（一次 e2e 用例）：**
`run_tests.py` 读 `config.toml` → `builder` 调 cmake/make 产出 `del2d.exe` → `runner` 在 `models/del2d1.gid/` 跑 `del2d.exe del2d .` 产出 `del2d.post.res` → `comparator` 解析它与基准逐场逐节点对比 → `report` 记录 `max|Δ|` 与首个超差点。

## 4. 框架核心组件（薄层 + 统一用例接口）

遵循 SOLID：框架只依赖一个抽象接口 `Case`，四个工具模块是无状态服务；四层套件是 `Case` 的不同实现，新增套件类型**不改框架**（开闭原则）。

```
run_tests.py
   │ 读 config.toml → 构造 Case 实例列表
   ▼
┌─────────────────────────────────────────────┐
│  Case（统一接口，四层套件各实现）              │
│    run(ctx) -> CaseResult                    │
│      ├──► builder.build(targets) -> exe 路径  │
│      ├──► runner.run(exe, args)  -> RunResult │
│      └──► comparator.compare(a, b) -> CompareResult│
└─────────────────────────────────────────────┘
   │ 每个 Case 产出 CaseResult
   ▼
report.aggregate([CaseResult]) -> 报告 + 退出码
```

**关键接口签名（Python）：**

```python
class Case(Protocol):
    name: str            # "e2e.del2d1"
    suite: str           # "e2e" | "unit" | "generator" | "analytical"
    def run(self, ctx: "TestContext") -> "CaseResult": ...

@dataclass
class CaseResult:
    name: str
    status: str          # "pass" | "fail" | "error" | "skip"
    metric: dict         # {"max_abs_err": 1e-12, "n_points": 2343, ...}
    detail: str          # 失败时：首个超差点的可读定位

class Builder:
    def build(self, targets: list[str]) -> dict[str, Path]: ...  # cmake+make，缓存 target

class Runner:
    def run(self, exe: Path, args: list[str], cwd: Path,
            expect_outputs: list[str]) -> RunResult: ...         # subprocess + 收集产出 + 超时

class Comparator:
    def compare(self, actual: Path, baseline: Path,
                tol: Tolerance) -> CompareResult: ...            # 只返回误差，不判 PASS/FAIL

class Reporter:
    def aggregate(self, results: list[CaseResult]) -> int: ...   # 返回退出码
```

**职责边界（KISS，每模块一件事）：**
- `Builder`：输入 target 名 → 输出 exe 路径，缓存已构建 target（DRY）。
- `Runner`：跑一个 exe + 收集指定产出文件，超时与退出码归它。
- `Comparator`：两个 `.res` 数值对比，返回结构化误差，**不判 PASS/FAIL**（判据外置到 Case/容差）——可被 e2e 与 analytical 复用。
- `Reporter`：聚合展示，决定进程退出码（`0`全过 / `1`有 fail / `2`框架 error）。

## 5. 四层测试套件（优先级重排）

**优先级：`e2e 回归`（核心）≫ `unit 快速反馈` > `analytical 接口` > `generator 可选`**

### 5.1 基准双层锚定（核心设计点）

| 基准层 | 含义 | 覆盖 | 容差 | 作用 |
|---|---|---|---|---|
| **regression（稳定性）** | 冻结当前正确输出，改库后检测漂移 | **全 7 sample** | 1e-12 | 用户核心诉求：基础库改了结果不变 |
| **accuracy（正确性）** | 对齐旧 C 基准/解析解，证明"冻结值"可信 | 有基准者：del2d→newmark、El2D→el.exe | 1e-10 | 先验证再冻结，避免错误冻成基准 |

**流程**：`accuracy 通过（或人工确认）→ 冻结为 regression 基准 → 之后每次改库跑 regression`。无旧 C 基准的 sample（truss 系列）人工确认后直接冻结 regression 基准，待补解析解。

### 5.2 e2e 扩到全 7 sample（覆盖基础库所有路径）

| sample | 路径覆盖 | accuracy 基准 | regression 基准 |
|---|---|---|---|
| `del2d1` | 动力学 Newmark + 体单元 + 边单元 + 应力恢复 | newmark.exe ✅ | 冻结 |
| `hel2d1` | 热固耦合（温度 + 位移） | 待补 | 冻结 |
| `el2d1` | 静力平面 + Q4 + T3 + 面力局部坐标变换 | el.exe ✅ | 冻结 |
| `truss1D/2D/3D` | 杆单元 1/2/3D | 待补解析解 | 冻结 |
| `ElT3` | T3 三角形单元 | 待补 | 冻结 |

→ 新增用例只改 `config.toml`，不动代码（DRY）。

### 5.3 e2e 用例运行

```
E2ECase.run():
  builder.build(["del2d"])
  runner.run(del2d.exe, ["del2d","."], cwd=models/del2d1.gid,
             expect=["del2d.post.res"])
  comparator.compare(产出.res, 基准.res, tol=1e-12)
```
注册：`[[suites.e2e]] name="del2d1" project="del2d" case_dir="models/del2d1.gid" baseline="del2d.post.res" tol=1e-12`

### 5.4 unit 聚焦"易因基础库改动而坏的机制"（快速反馈）

e2e 慢（全构建全跑），unit 快（毫秒级断言）。针对 rules 点名的基础库陷阱首批写：
- `EquationSystem`：`adda` 行主序落位、`applyFirstBCs` 划行幂等、`_bSavedData0` 刷新必要性、`calRightVals` 用 `_data0`
- `StressBL2g.coordTransform`：局部坐标轴正交性（2 节点线切向/法向）

构建：`test/suites/unit/CMakeLists.txt` 编译 `catch_main.cpp` + `test_*.cpp`，**链接 CDFEG SHARED 库**，产出 `cdfeg_unit_test.exe`。`UnitCase.run()` 跑 exe 并解析 Catch2 输出（退出码 0=全过）。

### 5.5 generator 弱化为可选独立项

- **不进主回归流程**（`--suite all` 默认不含），因生成代码对比无意义。
- 仅保留 pyTool **解析正确性**断言（pre/ges/gcn 解析不退化），用 pytest，需显式 `--suite generator`。

### 5.6 analytical 留接口（首批空）

`AnalyticalCase`：跑出结果后只取 `check_points`（关键节点/分量），与 Python 解析公式比相对误差。与 e2e 区别：e2e 比整个 `.res`（基准=旧 C，绝对容差）；analytical 比关键点（基准=物理，相对容差 1e-6）。首批只实现 Case 类与空注册。

## 6. `.post.res` 解析与数值对比引擎

### 6.1 GiD 结果文件格式（权威依据）

来源：[GiD 17 Customization Manual](https://downloads.gidsimulation.com/GiD_Documentation/Docs/GiD17/GiD_17_Customization_Manual.pdf)、[GiD Reference Manual - Postprocess Data Files](http://www-opale.inrialpes.fr/Aerochina/info/en/html-version/gid_17.html)。

语法：
```
GID Post Results File 1.0
Result "<结果名>" "<分析名>" <步号> <类型> <位置>
ComponentNames "<分量1>" "<分量2>" ...
Values
    <实体号> <v1> <v2> ...
    ...
End Values
```
- 类型：`Scalar` / `Vector` / `Matrix` 等；位置：`OnNodes` / `OnGaussPoints`
- 实体号可不连续（GiD 允许 holes）
- 实测：`del2d.post.res` = 11 步 × 4 段（`disp`/`velocity`/`acceleration`/`stress`），`stress` 为 Matrix 3 分量 sigmaXX/sigmaYY/sigmaXY

### 6.2 解析数据模型

```python
# ResFile = {(result_name, step): ResBlock}
@dataclass
class ResBlock:
    result_name: str          # "disp"
    analysis: str             # "Load Analysis"
    step: int                 # 3
    result_type: str          # "Vector" | "Scalar" | "Matrix"
    location: str             # "OnNodes" | "OnGaussPoints"
    components: list[str]     # ["u", "v"]
    values: dict[int, list[float]]  # {节点号: [v1, v2]}  按节点号对齐（容 holes）
```
正则锚点：`^Result "..." "..." <step> <type> <loc>`、`^ComponentNames`（按引号切分）、`Values`…`End Values` 间逐行 `split()`。Matrix 分量按 `ComponentNames` 顺序对齐，**不硬编码** sigmaXX/YY/XY（兼容不同场）。

### 6.3 两段判定（Comparator）

**第 1 段 · 结构一致性（回归的硬信号）**，先于数值检查：

| 检查项 | 判定 |
|---|---|
| result_name 集合 | actual==baseline？否则报"结果段增减" |
| 每段 step 集合 | 否则报"步数漂移"（捕获 nStep 差 1 陷阱） |
| 每段 components | 否则报"分量变化" |
| 每段 entity 节点集合 | 否则报"节点集合变化" |

→ 任一不符即 `status=fail(structural)`，直接 FAIL，**不进入数值对比**（结构变了数值对比无意义）。

**第 2 段 · 数值逐点对比**（仅当结构一致）：
```python
for (name, step) in blocks:
    for node in values:
        for i, comp in enumerate(components):
            delta = abs(actual - baseline)
            passed = delta <= atol + rtol * abs(baseline)   # 绝对+相对双容差
```
统计：`max_abs_err`、`n_over_tol`、`first_over`（首超差点）、`worst_point`（全局最大误差点）。

### 6.4 容差分层

| 用途 | atol | rtol | 理由 |
|---|---|---|---|
| regression（同库同工具链重跑） | **1e-12** | 0 | 同环境重跑近位级一致，留浮点余量 |
| regression（跨构建，如换编译器） | 1e-8 | 1e-9 | 编译器差异致末位抖动 |
| accuracy（对齐旧 C 基准） | **1e-10** | 0 | rules 已验证 del2d 对齐 newmark 到 1e-10 |

→ 默认 regression(同库) 1e-12；accuracy 用例在 config 单独配 1e-10。

### 6.5 失败报告样例

```
FAIL  e2e.del2d1  [structural] step 集合漂移: disp 段 actual={1..11} baseline={1..12}
      → 疑似 nStep 回归（rules: nStep 差 1 陷阱）

FAIL  e2e.del2d1  [numeric] max|Δ|=4.3e-7  超差点 1/2343
      首超: result="disp" step=3 node=42 comp="v" actual=-1.021e-5 baseline=-1.025e-5
      最差: result="stress" step=7 node=88 comp="sigmaXY" |Δ|=4.3e-7
```

## 7. 基准更新、错误处理与构建集成

### 7.1 构建集成（复用 FEMproject 根 CMake，DRY）

测试系统把 `FEMproject/` 当构建根（已 `add_subdirectory` 全部 sample + CDFEG，已验证可用）。仅加开关引入 unit test target：

```cmake
# FEMproject/CMakeLists.txt 末尾新增
option(CDFEG_BUILD_TESTS "构建 CDFEG 测试系统" OFF)
if(CDFEG_BUILD_TESTS)
    add_subdirectory(${CMAKE_CURRENT_SOURCE_DIR}/../test/suites/unit
                     ${CMAKE_BINARY_DIR}/cdfeg_unit_test)
endif()
```

`builder` 执行（贴合 rules §10 cygwin 命令；target 名取自各 sample 的 `add_executable`）：
```bash
cmake -B test/build -S FEMproject -G "Unix Makefiles" -DCDFEG_BUILD_TESTS=ON
cmake --build test/build --target del2d hel2d el2d ElasticT3 Truss1D Truss2D Truss3D cdfeg_unit_test -j
```
（实际 target 名：`del2d`/`hel2d`/`el2d`/`ElasticT3`/`Truss1D`/`Truss2D`/`Truss3D`，均来自各 `sample/*/CMakeLists.txt` 的 `add_executable`。）
→ 可执行落 `test/build/output/`（遵循全局 build/out 规范）；option 默认 OFF 不干扰日常构建；增量构建由 make 处理，builder 缓存 `-B` 避免重复 configure。

### 7.2 基准更新 `--update`（显式 + 安全护栏）

```bash
python run_tests.py --suite e2e --update del2d1
```
流程：跑 builder+runner 产出 actual → **与旧基准对比打印 diff 摘要**（结构变化 + max|Δ|）→ 暂停等回车确认 → 落地覆盖基准 → 打印 `git add` / `commit` 提示。

**护栏（防 bug 冻结）：**
- **禁用 `--update all`**：必须逐个 `--case`，强制人工过目每个变更。
- 覆盖前**强制打印 diff 摘要并暂停等回车**，不静默覆盖。
- accuracy 与 regression 基准**分文件存**（`del2d.post.res` regression vs `del2d.post.res.accuracy`），更新 accuracy 需额外 `--update-accuracy` 标志。
- 更新记入 `reports/update_log.txt`（时间/用例/max|Δ|/原因占位）。

### 7.3 状态分级与错误处理

`CaseResult.status` 四态，**区分"测试基础设施问题"与"真实回归"**：

| status | 含义 | 触发 |
|---|---|---|
| `pass` | 通过 | 结构一致且数值在容差内 |
| `fail` | **真实回归**（要捕捉的） | 结构漂移 / 数值超差 |
| `error` | 基础设施问题 | cmake/make 失败、exe 崩溃/超时/非零退出、产出缺失 |
| `skip` | 配置跳过 | config 标 `skip=true` |

→ `error` 与 `fail` 都计未通过，但报告分栏：`fail` 是关注重点，`error` 提示先修测试设施。构建/运行日志落 `reports/<case>.log`。

### 7.4 CLI 与报告

```bash
python run_tests.py                      # 默认 all = e2e + unit（不含 generator）
python run_tests.py --suite e2e --case del2d1
python run_tests.py --suite e2e --update del2d1
python run_tests.py --suite generator    # 显式（默认不含）
python run_tests.py --rebuild -v         # 强制重 configure + 详细输出
```
报告：终端汇总表（用例 × status × max|Δ|）+ 失败详情；归档 `reports/<时间戳>.txt`。退出码 `0`全过 / `1`有 fail / `2`框架 error。

## 9. 验收标准与首批交付物

### 9.1 首批交付（MVP）

1. `test/run_tests.py` + `test/config.toml` 入口与配置
2. `test/framework/`：builder / runner / parser / comparator / report 五模块
3. `test/models/`：保留现有 `del2d1`/`hel2d1` 基准，补 `el2d1`（对齐 `FEMproject/test/el2dData/el.exe`）
